## 4. DI Lifetime Audit (Phase 5.1 expansion)

The plan flagged **one** captive-dependency bug (`Point130SoldPriceService` Singleton+DbContext at `App.axaml.cs:135`). Auditing the rest of `App.axaml.cs:83-153` against `Web/Program.cs:31-88` reveals **three more potential issues** in Desktop where Web has already corrected the lifetime:

| Service | Desktop lifetime | Web lifetime | Web comment | Verdict |
|---|---|---|---|---|
| `ISoldPriceService` (Point130) | Singleton (line 135) | **Scoped** (line 82) | "Depends on DbContext" | **Confirmed bug** (already in plan) |
| `IPricerService` | Transient (line 123) | **Scoped** (line 70) | "Depends on DbContext via repositories" | **Likely bug** — verify constructor takes DbContext |
| `IExportService` (CsvExportService) | Transient (line 132) | **Scoped** (line 78) | "Depends on DbContext" | **Likely bug** — verify constructor |
| `IVariationVerifier` (VariationVerifierService) | Transient (line 133) | **Scoped** (line 80) | "Depends on DbContext" | **Likely bug** — verify constructor |

Transient + DbContext is less catastrophic than Singleton + DbContext (the captive scope problem only bites long-lived consumers), but it's still inconsistent with Web and against EF Core best practice — Transient consumers can outlive their DbContext scope and hit `ObjectDisposedException`.

**Action:** Phase 5.1 must verify each service's constructor and align Desktop with Web. Add to plan as part of "audit every other registration."

Services confirmed correct as Singleton (no DbContext deps):
- `XimilarService` — takes HttpClient + ISettingsService
- `OpenRouterScannerService` — takes HttpClient + ISettingsService (verified)
- `CompositeScannerService` — composes the two scanners above
- `IChecklistLearningService` — takes IServiceProvider (intentional scope-creating pattern)
- `IBulkScanErrorLogger` — no DI deps

### 5.9 Bug discovered during Phase 4b: OpenRouterScannerService retry filter is broken for 5xx / 429 — **FIXED in Phase 5a**

While writing scanner tests, the fallback chain logic was found to be silently broken for non-404 retryable errors.

**Where:** [`FlipKit.Core/Services/Implementations/OpenRouterScannerService.cs:369-376`](../FlipKit.Core/Services/Implementations/OpenRouterScannerService.cs#L369-L376) — `IsRetryableHttpError`.

**Bug:** The check looks for digit substrings (`msg.Contains("500")`, `"502"`, etc.) in the exception message. The exception is constructed at line 333 as `$"OpenRouter API error ({response.StatusCode}): {responseBody}"` where `response.StatusCode` formats as the enum *name*, not the integer (`"InternalServerError"`, `"ServiceUnavailable"`, `"TooManyRequests"`, etc.). Net effect: **the `when` filter never matches for 5xx or 429**, the exception isn't caught, and the fallback chain is never walked. Only 404 works — because the check explicitly has `msg.Contains("NotFound")`.

**Fix (Phase 5):** Either (a) check `(int)response.StatusCode` directly when constructing the exception or rethrow with the integer in the message, or (b) update `IsRetryableHttpError` to check the enum names alongside the digits. Option (a) is cleaner because it keeps the retry classification co-located with the HTTP call, but (b) is a one-line change to a single helper. Pick during Phase 5 implementation.

**Resolution:** Picked option (a) in Phase 5a. Throw site at `OpenRouterScannerService.cs:333` now includes both the integer status code and the enum name in the exception message. Existing test that documented the workaround was updated, and a new positive test (`Should_FallBackOn5xx_When_FirstModelReturnsServerError`) confirms the fix.

### 5.10 Bug discovered during Phase 4b: SetChecklist JSON-column mutations are silently lost — **FIXED in Phase 4.5**

**Where:** [`FlipKit.Core/Data/FlipKitDbContext.cs:105-113`](../FlipKit.Core/Data/FlipKitDbContext.cs#L105-L113) — `SetChecklist.Cards` and `SetChecklist.KnownVariations` are persisted as JSON columns via `HasConversion(serialize, deserialize)` but **without a `ValueComparer`**.

**Bug:** EF Core's change tracker can't detect mutations to collection-typed properties when the underlying reference doesn't change. So `checklist.Cards.Add(newCard)` followed by `SaveChangesAsync()` is a no-op — EF doesn't know the property changed. The entire "enrich existing checklist" code path in [`ChecklistLearningService.LearnFromCardAsync` (lines 128-173)](../FlipKit.Core/Services/Implementations/ChecklistLearningService.cs#L128-L173) silently fails in production: every learning pass after the first never persists anything.

**Impact:** Roadmap #1 Checklist Insider import depends on `ChecklistLearningService` for the post-import enrichment flow (Surface B). The bug means imports work the *first* time but updates never stick.

**Fix (Phase 5):** Add `ValueComparer<List<T>>` to both conversions. Pattern:
```csharp
.HasConversion(
    v => JsonSerializer.Serialize(v, ...),
    v => JsonSerializer.Deserialize<List<ChecklistCard>>(v, ...),
    new ValueComparer<List<ChecklistCard>>(
        (l, r) => JsonSerializer.Serialize(l, ...) == JsonSerializer.Serialize(r, ...),
        l => l == null ? 0 : JsonSerializer.Serialize(l, ...).GetHashCode(),
        l => JsonSerializer.Deserialize<List<ChecklistCard>>(JsonSerializer.Serialize(l, ...), ...)));
```
After the fix, re-enable [`ChecklistLearningServiceTests.Should_AppendNewCardAndVariation_When_ChecklistAlreadyExists`] (currently `[Fact(Skip = ...)]`).

**Resolution:** Fixed in Phase 4.5 (out-of-band bug-fix interlude between 4b and 4c). `ValueComparer<List<ChecklistCard>>` and `ValueComparer<List<string>>` added to both conversions. Test un-skipped. Suite at 246/246 passing.
